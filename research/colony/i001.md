# Move acceptance into an independent sandboxed evaluator

Task `I001`; base revision `2688e0e3644215f0530f1a3ec736059a7fe8157a`.

## Task I001 research artifact

**Scope:** Read only. No repository files or policies were changed. I inspected the evaluator, comparator configuration, CI workflow, proof sources, and recorded evidence.

### Current implementation

- Lean is pinned to `leanprover/lean4:v4.35.0`. The checked-in seed report records eight positive proofs accepted by Lean’s elaboration kernel and a false claim rejected. That report explicitly says it has **no independent replay**.
- `lean/comparator.json` names eight theorem roots, permits only `propext`, `Quot.sound`, and `Classical.choice`, and configures `lean4lean --import`. The separate `Challenge.lean` contains matching theorem statements. The Linux CI workflow installs Bubblewrap and runs `lake comparator`.
- The evaluator’s manifest and challenge lock live in the same repository as the worker’s solution. They detect accidental drift, but do not establish independently controlled challenge ownership.
- A controller-side GitHub broker exists. Documentation describes worker restrictions and the broker, while also identifying process and credential isolation as incomplete. This does not demonstrate VM/container isolation or an independently administered publication boundary.

### Checks and evidence

- Inspected the existing report and configuration; **did not run** the evaluator, tests, or comparator, since those checks can write generated files or require the sandbox.
- Environment inspection found `lake`, but no `bwrap` or `lean4lean` executable; the host reports Darwin. Thus I could not verify a sandboxed comparator run or external-kernel replay here.
- Checked-in documentation reports a prior macOS sandbox attempt that exited before any checker ran, and describes the Linux comparator gate. Those are recorded claims, not results reproduced in this read-only session.

### Remaining trust and platform limits

Independent challenge ownership and configuration control remain unresolved. The Python evaluator and its output parser are not an adversarial security boundary. Current documentation also identifies missing disposable VM/container isolation and the need for a scoped publication broker; the existing broker is controller-side, but its presence alone does not prove those controls. The task’s acceptance criteria are therefore **not established by this read-only investigation**.
