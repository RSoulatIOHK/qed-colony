Their public documentation describes `#prep_uplc` as producing both an optimized `prop` expression and original `exec` expression, with a CEK step bound; the Ledger API library documents V1–V3 context types, validity predicates, and `IsData` conversions. ### Semantic bridges and proof obligations

1. **Artifact provenance and identity.** Freeze the validator source, language/compiler and settings, exact compiled bytes, serialization envelope, ledger language version, and hashes. Pin immutable commits for PlutusCoreBlaster, CardanoLedgerApiBlaster, Blaster, Lean, and transitive dependencies. Confirm the bytes and script hash agree with the artifact under test. A theorem about a Lean term only applies to the artifact identified by this record.

2. **Decoding.** For the exact Flat/CBOR/hex import mode, establish that decoding is total on the accepted input or returns an explicit decode failure; test malformed, truncated, and wrong-version inputs. Show the decoded AST and version correspond to the supplied bytes and language tag. Do not treat a successful parser run as evidence that the encoded artifact was the intended deployed script.

3. **Input and `Data` conversion.** Audit datum, redeemer, and context construction, including constructor tags, field order, integer/byte encodings, and every `IsData` round trip or partial decode. State how malformed encodings behave. Prove conversion correctness for the selected types, and verify the values passed to the imported program are the values represented by the ledger-facing input.

4. **Preprocessing and application.** For each transformation used to create `prop`—including input application, normalization, or simplification—prove it preserves observable CEK outcomes under stated assumptions, or avoid relying on it in the theorem. Relate `prop` to the original `exec`; solver success about `prop` alone is not enough.

5. **UPLC and CEK semantics.** Compare term constructors, evaluation order, strictness, environments, errors, and state transitions with the selected Plutus semantics/reference implementation. Prove the evaluator’s step-limited and budget-aware paths preserve the intended outcome classifications. For budget claims, include the applicable protocol cost model and parameter version: a step count is not by itself a CPU/memory budget.

6. **Builtins and cryptography.** Inventory every builtin reachable in the target and its version-specific behavior, partial/error cases, byte and integer edge cases, and cost accounting. For cryptographic builtins, identify the implementation and trust boundary; validate against upstream vectors and differential tests, and prove implementation correctness where a proof is claimed. Test vectors are useful conformance evidence but do not prove correctness for all inputs. PlutusCoreBlaster documentation lists cryptographic coverage and says the conformance suite is separately generated and run; it also notes some features remain unimplemented. [Conformance and current scope](https://github.com/input-output-hk/PlutusCoreBlaster)

7. **Ledger context and validity.** For the selected ledger era and script API version, map transaction bytes and ledger-produced context to the Lean context fields. Audit each premise in the relevant `valid*Context` predicate against the node ledger rules, including purpose, inputs/outputs, datum witnesses, sortedness, values, fees, and balance. Establish that the modeled domain neither admits impossible contexts nor omits relevant valid ones for the theorem.

8. **Property and assurance.** State the exact property over the original imported script, contexts, assumptions, and resource bound. Ensure all reductions and proof reconstruction preserve that statement. Record precisely whether evidence is Lean elaboration/kernel acceptance, exported replay, independent-kernel acceptance, reference-implementation conformance, or an end-to-end correspondence result; these are distinct assurance claims.

### Outcome and non-vacuity requirements

Keep evaluator outcomes separate:

- **Fuel or budget exhausted:** unknown/incomplete for that resource bound; never count as success, failure, or a proof of rejection.
- **Script failure:** an explicit UPLC/CEK error result under the selected semantics. Distinguish it from malformed input, decode error, and evaluator failure.
- **Script success:** explicit successful result under the selected semantics and bound.

For each safety claim, require at least one valid successful transaction witness. Also require valid failing cases and intentionally invalid contexts that the ledger-validity premise rejects. For vulnerability checks, provide a valid attack witness and replay it through the pinned reference evaluator/ledger path. This prevents an empty or over-restricted premise from making a safety theorem vacuously true.

### Reproducible first target

Start with the documented **SellNFT** spending-validator example in `CardanoLedgerAPIBlaster`, whose stated properties concern seller payment and whose documentation describes a multi-satisfaction vulnerability. It is a bounded, ledger-connected target with useful positive and attack cases. [SellNFT example](https://github.com/input-output-hk/CardanoLedgerAPIBlaster)

Before calling it reproducible, freeze its exact example source and compiled script: the documentation page does not itself provide immutable dependency revisions or a script digest. Record the source revision/path, compiler and flags, raw `.flat` and serialized envelope hashes, script hash, Plutus language version, all dependency commits, Lean toolchain, and the exact evaluator/conformance commands. Then preserve the documented seller-payment property, add valid success/failure witnesses, and record a multi-satisfaction counterexample. The repository documentation describes Lean 4.24.0 as the library prerequisite; the local pilot is pinned to Lean 4.35.0, so compatibility must be established rather than assumed.
